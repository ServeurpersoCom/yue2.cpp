# YuE2 Studio audit — 27 September 2026

## Repair update

Items 1–6 have since been implemented and regression checked. See [reliability repairs](reliability-repairs-2026-09-27.md) for the changes, evidence and limits. The findings below preserve the original audit baseline; items 7–20 remain outstanding unless explicitly noted in that repair report.

## Assessment

The app has functioning music generation, planning/voices, lyric assistance, saved tracks, original/master comparison, artwork integration, MP4 export and substantial UI polish. It is not yet a fully resilient production workflow. The most important remaining work is saving and recovering work safely, coordinating long operations, and completing the partially implemented publishing/album workflows.

This audit changed no application source or production data and restarted no live service. It added this report and disposable audit fixtures under `build/`.

## Evidence and limits

- Live YuE2 health passed on port 8087, PID 24296, `build/Release-reference/yue-server.exe`.
- ComfyUI responded on 8188; queue was empty and required Qwen image nodes were present. This proves readiness, not image quality or successful inference. No recent history entries were returned by the history probe.
- Ollama responded; both Tiger-Gemma names were installed. No model was resident at the time of the audit, which is compatible with the lyric code's `keep_alive: 0` behavior.
- Svelte check: **0 errors, 0 warnings**.
- Existing frontend unit suites: **18 passed**. YouTube draft validation: **3 passed**.
- Separate CPU server smoke checks passed: defaults, six invalid requests, oversized request and embedded UI. No songs generated.
- New isolated browser cases reproduced four failures: empty-library navigation, unavailable local storage, invalid saved request and unsuccessful favourite persistence. Output: `build/ui-review/full-audit-findings.json`.
- Previous interaction review covered 244 visible controls with expanded panels/manual mode; six themes, phone width, keyboard interactions and representative operations passed. That was not proof that every backend operation and failure mode worked.
- No real synthesis, image inference, vocal separation or signed-in YouTube upload was performed in this audit. Large-library stress, simultaneous GPU operations, power-loss recovery and dependency vulnerability scanning remain unverified. Remote PR status was not refreshed.

## Priority 1 — protect work and prevent broken sessions

### 1. Storage failure or malformed saved settings can prevent the app from rendering

**Reproduced.** Making the `yue2` local-storage write throw a quota error left the Create heading absent with an uncaught exception. Saving `request.style: 42` caused `style.trim is not a function` and the same failure.

Evidence: [state.svelte.ts](../tools/webui/src/lib/state.svelte.ts), particularly the unvalidated `parsed.request` at line 38 and unguarded `setItem` at line 120.

**Needed:** validate/migrate persisted data, catch storage writes, keep the app usable in a clearly indicated unsaved mode, and provide an in-app settings recovery action. Add regression cases for quota, denied storage and malformed field types.

### 2. MP4 delivery delays saving successfully generated audio

**Confirmed from code.** `landJob` downloads the audio, then awaits image generation and video rendering; only afterward does it call `putJobSongs`. Ordinary caught failures eventually keep audio, but a browser close/crash plus server restart during those optional stages can lose the finished result before it reaches the library.

Evidence: [RequestForm.svelte](../tools/webui/src/components/RequestForm.svelte), lines 232–279.

**Needed:** commit audio immediately, then save artwork/video as separately recoverable updates to the existing track. Show the track as ready for playback while optional delivery work continues.

### 3. Server job recovery is temporary, not durable

**Confirmed from code.** Job results live in the process's `g_jobs` map. Completed jobs can be evicted after the 32-job retention limit; restarting discards the map. Browser recovery stores a job ID, not an independent copy of an unfinished/uncollected result.

Evidence: [yue-server.cpp](../tools/yue-server.cpp), lines 184–244; [db.ts](../tools/webui/src/lib/db.ts), pending-job functions.

**Needed:** a disk-backed job/result store, startup recovery, retrieval acknowledgement and retention controls. Make the distinction between a server result and a library-saved track visible.

### 4. Multiple tabs can overwrite or interfere with pending-job recovery

**Confirmed design gap; race not stress-tested.** All tabs share the single `yue2-job-synth` local-storage key. The check-before-submit sequence is not an atomic lock. Separate tabs can submit before either saves its job ID; a completion can then clear another tab's recovery record. There is no application-wide operation owner or coordinated library refresh.

Evidence: [RequestForm.svelte](../tools/webui/src/components/RequestForm.svelte), generation loop; [db.ts](../tools/webui/src/lib/db.ts), `saveJob`/`clearJob`.

**Needed:** per-job records, submission/ownership locking, cross-tab updates and owner-aware cancellation. Test simultaneous starts and reloads.

### 5. Some library actions show changes before they are safely saved

**Favourite failure reproduced.** When IndexedDB writes failed, the heart became selected, no error toast appeared and an uncaught exception was raised. Rename, generated-artwork and vocal processing also mutate live song state before the awaited save. Delete handlers have incomplete failure reporting. A long operation can also save a track after the user deleted it because its completion still calls `putSong`.

Evidence: [SongCard.svelte](../tools/webui/src/components/SongCard.svelte), `toggleFavorite`, `doRename`, `generateArtwork`, `applyVocalBalance`, deletion and asynchronous completion handlers. The rail's favourite handler already uses a safer save-before-display approach.

**Needed:** shared transactional song updates, visible failure/retry, rollback or save-before-display, and deletion/operation coordination that prevents deleted tracks from reappearing.

### 6. Backups omit current disk presets and accept insufficiently validated restored data

**Confirmed from code.** The ZIP includes songs and a fixed list of old browser keys, but not the new `saved_presets` folder. Restore validates little beyond audio Blob, name and truthy request; missing/wrongly typed format/style/request fields can reach components expecting valid strings and objects. The malformed-settings browser test demonstrates why this matters.

Evidence: [backup.ts](../tools/webui/src/lib/backup.ts), `LOCAL_STORAGE_KEYS`, `exportLibrary`, `importLibrary`; [SongList.svelte](../tools/webui/src/components/SongList.svelte), settings restore.

**Needed:** versioned full backup schema covering disk presets and current settings; validate everything before replacing the library; offer a pre-restore backup and explain exactly what is included. The normal disposable backup/restore round-trip already passes.

## Priority 2 — make long workflows and saved outputs consistent

### 7. Cancel does not cancel the whole MP4 workflow

**Confirmed from code.** `cancelPipeline` only calls the music job cancellation endpoint and stops remaining takes. Artwork polling has no abort signal, and the video request has no cancellation mechanism. Cancelling after music completes can leave artwork/video continuing while the UI still looks busy.

Evidence: [RequestForm.svelte](../tools/webui/src/components/RequestForm.svelte):504; [track-artwork.ts](../tools/webui/src/lib/track-artwork.ts); [api.ts](../tools/webui/src/lib/api.ts), `renderVideo`.

**Needed:** stage-specific cancellation and explicit “stop waiting” versus “cancel owned work” behavior, preserving completed audio and never cancelling unrelated Comfy jobs.

### 8. Artwork recovery differs between entry points

**Confirmed from code.** Automatic MP4 generation saves the Comfy prompt ID. On-demand Export video does not persist its artwork job ID. Generate artwork from the track menu keeps its ID only inside the function; closing the dialog stops polling but leaves the Comfy job running. Reload/navigation can therefore orphan an image result from the app's perspective. Some errors refer to resetting an album stage that the song-card UI does not expose.

Evidence: [track-artwork.ts](../tools/webui/src/lib/track-artwork.ts); [SongCard.svelte](../tools/webui/src/components/SongCard.svelte), `exportVideo` and `generateArtwork`; [comfy-art.ts](../tools/webui/src/lib/comfy-art.ts).

**Needed:** one persistent artwork operation model, recover completed results by prompt ID, visible retry/reconnect and consistent errors for the actual screen.

### 9. Existing MP4s and waveforms can become stale after edits

**Confirmed from code.** Replacing/generating artwork retains the old `song.video`. Vocal adjustment replaces audio but retains both the old video and cached peaks. The waveform reuses `song.peaks` when present, so it can show the previous audio's waveform. The downloaded MP4 can contain an older cover/mix than the current card.

Evidence: [SongCard.svelte](../tools/webui/src/components/SongCard.svelte):74, 168, 293; [Waveform.svelte](../tools/webui/src/components/Waveform.svelte):88–110.

**Needed:** invalidate/recompute peaks on audio replacement; record the audio version and artwork revision used in each MP4; mark video outdated and offer a rebuild when inputs change.

### 10. Expensive services are not coordinated under one scheduler

**Confirmed architecture gap; resource exhaustion not reproduced.** Native synthesis/transcription use the bounded worker queue. Video and vocal-balance handlers run synchronously outside it. Artwork and Ollama have separate checks. Per-card busy flags do not coordinate other cards, tabs or services; `freeArtworkMemory` is defined but unused. Subprocess waits lack a timeout/cancellation mechanism.

Evidence: [yue-server.cpp](../tools/yue-server.cpp):867, 919; [audio-video.h](../src/audio-video.h); [audio-vocal-balance.h](../src/audio-vocal-balance.h); [comfy-art.ts](../tools/webui/src/lib/comfy-art.ts).

**Needed:** bounded operations for video/vocals, shared GPU ownership where appropriate, server-side operation status, subprocess cancellation/timeouts and measured memory handoff between models. Readiness should also check encoder/separator dependencies before a long action starts.

### 11. “Save preset” still means two different things

**Confirmed from code.** Named music/lyric blends save into the folder and sidebar. The top-level Save preset button still downloads JSON/YAML and does not save a named full configuration there. A blend does not represent the whole planner/voices/output setup. Blend editors load their lists on mount and do not subscribe to the same preset-change event as the sidebar, so edits in another tab/editor can leave stale choices.

Evidence: [RequestForm.svelte](../tools/webui/src/components/RequestForm.svelte):309; [BlendFavourites.svelte](../tools/webui/src/components/BlendFavourites.svelte); [SavedPresets.svelte](../tools/webui/src/components/SavedPresets.svelte).

**Needed:** distinguish named full presets from style blends and file export, unify refresh behavior, and provide a clear naming/save destination flow.

### 12. Interrupted preset writes lack automatic recovery

**Confirmed crash window, not power-loss tested.** Existing preset JSON is renamed to `.bak` before `.tmp` is renamed into place. A crash between those operations leaves the preset absent from listing; subsequent saves reject the remaining backup. Rename of a preset is a multi-request save/delete operation and can partially complete.

Evidence: [saved-presets.h](../src/saved-presets.h), save handler; [BlendFavourites.svelte](../tools/webui/src/components/BlendFavourites.svelte), `commit`.

**Needed:** startup reconciliation for temporary/backup files and a transactional server rename/update operation with conflict detection.

### 13. Progress/ETA is not a complete job tracker

**Confirmed limitation.** The percentage/ETA measures the current NAR chunk, not the whole song. Status is derived from global log text and local tab state, so unrelated jobs and replayed log history can affect interpretation; another tab can show Ready while the server is working. Artwork and video lack measured progress. Remaining planned takes are not resumed after reload.

Evidence: [activity.svelte.ts](../tools/webui/src/lib/activity.svelte.ts); [LogCard.svelte](../tools/webui/src/components/LogCard.svelte); RequestForm's take loop.

**Needed:** job-scoped structured stage events, queue position, stage-specific estimates and a persisted take queue. Continue labelling estimates honestly until enough measurements exist.

### 14. Navigation has hidden-target and duplicate-panel problems

**Empty-library link reproduced.** “Shape your first track” changes the hash but leaves Library visible and Create hidden. Create remains mounted with `display:none` while Library adds another StudioRail; this also duplicates the settings target and log subscription. Settings links can target the hidden copy, and preview playback can continue from the hidden Create view.

Evidence: [SongList.svelte](../tools/webui/src/components/SongList.svelte):77; [App.svelte](../tools/webui/src/App.svelte):126 and library rail; [StudioRail.svelte](../tools/webui/src/components/StudioRail.svelte).

**Needed:** centralized view navigation, unique section IDs, intentional playback behavior on view changes and one shared activity subscription.

### 15. Invalid audio fails silently

**Confirmed from code.** Audio import saves a file based on its extension without first validating decode. Waveform decoding catches and discards errors. A broken/unsupported file can become a nonworking card without a useful explanation; Play can appear selected despite no decoded audio.

Evidence: RequestForm `openAudio`; [Waveform.svelte](../tools/webui/src/components/Waveform.svelte):110.

**Needed:** validate imports, show decoding/loading/error states, disable playback when unavailable and provide a retry/remove route.

### 16. Large-library memory use needs measurement and limits

**Confirmed eager-loading design; stress impact unmeasured.** The app gets all songs, mounts every visible song waveform and decodes full audio buffers. Library cards and preview can decode the same song separately. Job retention is bounded by count rather than bytes, and results include originals/masters. Video export reads the finished MP4 fully into memory.

Evidence: [db.ts](../tools/webui/src/lib/db.ts), `getAllSongs`; SongList's full list; Waveform's decoding effect; server job retention; audio-video output loading.

**Needed:** benchmark realistic libraries, lazy/shared audio decoding, list virtualization or pagination, byte-based retention and streamed/limited media handling where practical.

## Priority 3 — finish promised workflows and make releases repeatable

### 17. YouTube remains an assisted first version

**Confirmed implementation status.** Local draft editing/export and basic browser automation exist. Playlist, end screens, disclosures, scheduling and final save/publish remain manual. The UI requires downloading files and running a terminal command. The runner explicitly says a user-reviewed run is not verified publication; signed-in upload automation has not been exercised in the available evidence.

Evidence: [agent.mjs](../tools/youtube-agent/agent.mjs), [README](../tools/youtube-agent/README.md), [YouTubeDialog.svelte](../tools/webui/src/components/YouTubeDialog.svelte).

**Needed:** agree the remaining automation scope, test against a dedicated upload draft, handle changed/localized Studio selectors, resume existing uploads safely, and expose a clearer launch/status path. Keep publishing an explicit user action unless separately authorized.

### 18. Album creation is scaffolded, not a delivered workflow

**Confirmed from imports and UI.** Album types, database and planning helpers exist. No connected album runner/workspace completes the roadmap for a resumable track queue, master cover and distinct referenced track artwork.

Evidence: `album-types.ts`, `album-db.ts`, `album-plan.ts`; current App/RequestForm component tree.

**Needed:** implement the persisted album state machine, queue/resume controls, per-track retry, shared cover/reference workflow and export. Treat this as a feature project after reliability work, not a small UI addition.

### 19. Real media quality and adverse-condition tests remain incomplete

**Verification gap.** Unit/UI checks do not establish actual lyric quality, requested voice behavior, reference-image consistency, vocal separation quality, measured final loudness/true peak, long-track MP4 compatibility or recovery under resource exhaustion. Streaming/Broadcast are real FFmpeg loudness-normalization profiles, not a full creative mastering chain. Original/master pairing has three passing regression cases, so the previously reported duplicate-card issue has a targeted fix and coverage.

**Needed:** a documented media acceptance matrix with short real generation runs, multi-take runs, original/master measurements, actual generated artwork, reference edit, vocal balance, MP4 playback and interrupted-run recovery. Record which combinations were actually tested and the hardware/memory costs.

### 20. Current work is not packaged as a reproducible reviewed release

**Confirmed repository state.** There are 24 modified tracked files plus substantial untracked implementation/documentation. The running build includes work outside the last commit. Current interaction/theme audit scripts are under ignored `build/`; PR CI does not run the Svelte checks or these UI tests. Older audit/resume documents still describe already delivered artwork/MP4 features as unfinished and contain outdated launcher/deployment details.

Evidence: local Git status; [CI workflow](../.github/workflows/ci-build.yml); `AUDIT_REPAIRS.md`; `PROJECT_BUILD_PLAN.md`; `build/interaction-review.mjs` and related scripts.

**Needed:** curate persistent tests into the repository, add frontend checks/tests to CI, document one authoritative build/deploy/recovery route, refresh the status documentation, and make a reviewed commit/PR update. Do not include user media, model files, private browser profiles or temporary logs. Commit/push was not performed by this audit.

## Recommended execution order

1. **Prevent lost work:** findings 1–6. Pass quota, restart, multi-tab and full backup/restore scenarios before calling recovery reliable.
2. **Make long operations consistent:** findings 7–13. Save audio first; make artwork/video cancellable, resumable and revision-aware.
3. **Complete the everyday UI:** findings 14–16 and the preset workflow in 11. Fix navigation and playback errors, then measure large libraries.
4. **Run real media acceptance checks:** finding 19. Separate measured passes from model-dependent expectations.
5. **Package the release:** finding 20. Keep regression tests and current operations documentation with the source.
6. **Finish feature projects:** YouTube and albums (17–18) after their recovery foundations are in place.

No fixes were applied as part of this audit; the findings above remain open unless explicitly described as already covered/passing.
